# MemBench v0.2 — Experiment Redesign

**Status:** proposal, derived from the first full v0.1 run (`full-v01`, 75/75 rows) and from two design decisions recorded on 2026-07-31 that v0.1's plan contradicted.

## Why v0.1's shape must change

1. **The hand-written oracle should never have existed.** Recorded decisions (claude-mem #104460, #104468, 2026-07-31 — before the v0.1 plan was written): "perfect notes" do not exist objectively; note value is task-relative; the human-authored oracle was rejected as unscientific and redefined as a *task-aware model*. The v0.1 plan contradicted this and implementation followed the plan. Empirical confirmation: an observer model (deepseek-v4-flash) **beat** the hand-written "ceiling" 6/15 vs 5/15 — a ceiling that can be beaten is not a ceiling.
2. **60% of executor spend bought zero information.** On 3 of 5 corpus items every variant — including the oracle — scored 0/3: the executor (haiku-4.5 @ 60 steps) cannot do those tasks with any memory. Null cells distinguish nothing.
3. **`% of oracle savings` was undefined in every cell** — with a 0%-success floor there are no floor tokens to compare against. The metric was structurally broken, not incidentally.
4. **Tokens-to-done pooled across items is an artifact.** A model that succeeds on a cheap item and fails an expensive one "wins" on tokens without being more efficient anywhere.

## The redesigned experiment

### Claim, estimand, and unit of inference

MemBench v0.2 estimates **the effect of observer-written memory on downstream task success for the frozen, calibrated tasks, executor lane, model route, and budgets named by the run**. It does not claim that one observer is universally best across coding tasks, executors, or future provider versions.

- The corpus item is the primary unit of inference. The `k` repetitions estimate within-item stochasticity; they are not counted as `k` independent tasks.
- Comparisons are paired within `(item, executor lane)`: every observer and control sees the same task and starting commit.
- Aggregate deltas are computed from per-item rates. Where the calibrated item count is large enough, report paired uncertainty intervals by resampling items, never individual repetitions. Otherwise label the result descriptive and make no population-level claim.
- Record the requested and effective model/provider identifiers, prompt hashes, harness/SDK version, timestamps, and the randomized execution order. A seeded, round-robin schedule interleaves variants within each `(item, executor)` block so provider or machine drift cannot line up with one variant.
- A result may conclude **recommend**, **do not recommend**, or **insufficient evidence**. MemBench does not force a winner when the observed advantage is small, unstable across items, or supported by too few calibrated items.

### Controls

| Control | Definition | What it isolates |
|---|---|---|
| `none` (floor) | no memory | does memory matter at all |
| `shuffled` | another session's real model-written notes | relevance vs mere-context (kept — it caught a real "any context helps" effect on arenabench-001) |
| `oracle` (implementation id; reported as **task-aware reference**) | one fixed cheap model receives session N's transcript AND the N+1 task, writes observations in the standard schema, single call | a strong reference for task-aware *selection* |

**Reference grounding constraint — "task-aware selection, not task-aware invention":** every fact in the reference observations must be grounded in session N's transcript. The task tells the model *what to select*, never what to say. Generation emits non-injected provenance for every atomic fact: a transcript event id plus a short supporting quote. Verification checks that the event exists and the normalized quote occurs in that event; unsupported facts are struck before seeding. The provenance is retained for audit but removed from the executor's injection. This prevents the reference from smuggling the solution ("the fix is X") while keeping grounding mechanically reviewable.

`oracle` remains the on-disk/run-spec variant id for compatibility, but reports must not call it a true ceiling. A task-aware model is still fallible and a candidate may outperform it.

Hand-authored `oracle.md` files are retired (kept in item dirs as historical artifacts, excluded from runs and hashes going forward).

### Calibration gate (run before any scored matrix)

For each candidate item, at the run's executor + step budget, run a calibration attempt that is separate from and never reused in the scored matrix:

- floor, k=1 → must **fail**
- task-aware reference, k=1 → must **pass**

Only calibrated items enter the scored set. Items failing the gate are shelved with their evidence as `beyond-executor` (re-testable under a stronger executor), or `floor-solvable` (task needs no memory). Cost ≈ $1/item; the v0.1 run wasted ~$10 on 45 runs of structural zeros that this gate would have prevented.

The gate defines the target set as **tasks that demonstrated memory sensitivity in an independent pilot**; it is not evidence about all tasks. Because k=1 is deliberately a cheap, noisy screen, all scored repetitions are fresh. If their floor/reference behavior contradicts calibration, keep the item in the results and flag `calibration_instability`; never remove it after seeing scored outcomes.

### Metrics (defined once, computed per-item then aggregated)

**Headline (calibrated items only, per executor lane):**
- **Floor delta** = model success rate − floor success rate, averaged over items (never pooled across items).
- **Reference gap** = model success rate − task-aware-reference success rate, averaged over items. Positive values are valid: the reference is strong, not an assumed upper bound. A difference is used instead of a ratio so a weak or unstable reference denominator cannot amplify the result.

**Supporting:**
- **Memory-attributed hit rate** (per decision #104468): did the successful solution use a specific injected fact in a way visible in its trajectory, output, or diff? Judge-scored; the judge receives the injection block + the diff/output and must cite both the memory fact and the downstream consequence. Model identity and variant label are hidden. This remains supporting attribution evidence, not the causal headline; floor delta is the causal contrast.
- Search burden, drift rate, real reported cost — unchanged from v0.1.
- **Tokens-to-done**: reported per-item only; no cross-item pooling.

**Reported diagnostics (non-headline, per reframed goal in #104460):**
- **Schema adherence**: XML parse-failure rate per (model, item). v0.1 empirically proved this does not predict downstream value (deepseek went 3/3 on the item where it lost 40% of its notes) — which is exactly why it is reported as a property of interest, not a headline.

### What stays

- Frozen, sanitized, repo-pinned corpus items; check.sh-before-models discipline; k≥3; per-fork isolation; real-reported-cost-only accounting; lane separation; publish redaction; run governance (dry-run / ceilings / resume).

### Judge discipline

- Mechanical `check.sh` outcomes outrank model judgment. A completion signal is never treated as proof that the task succeeded.
- Pin the judge model and rubric version for a run. Hide observer identity, control label, model order, and aggregate scores from every judge prompt.
- Preserve raw judge replies and real reported usage. Transport failure or an invalid verdict stays `UNKNOWN`, never silently becomes a pass, no-drift, or no-hit result.
- Before publishing, re-judge a predeclared audit sample in shuffled order with an independent judge and report agreement. Material disagreement downgrades the affected supporting metric to exploratory.

## Ori-shaped result communication

Borrow Ori Eval's communication contract, not its experimental engine. The first page should answer three questions in plain language:

1. **Required behavior:** did memory provide and the executor use task-relevant evidence? (`memory-attributed hit`, plus retrieval-tool use only on cases whose rubric requires retrieval.)
2. **Avoided behavior:** did the run avoid misleading-memory failures, scope drift, and ungrounded claims?
3. **Outcome quality:** did the prewritten mechanical check or blinded rubric say the task was actually completed?

Lead with one compact decision table, one row per observer and separate sections per executor lane:

| Observer | Decision | Task success | Δ vs floor | Gap vs reference | Memory-attributed hits | Drift avoided | Real cost |
|---|---|---:|---:|---:|---:|---:|---:|

Follow it with:

- a one-sentence **recommend / do not recommend / insufficient evidence** call tied to a predeclared decision rule;
- the calibrated-item count and eligible-model coverage, so the denominator is impossible to miss;
- representative quoted failures with item ids, not only aggregate scores;
- a complete cost-and-timing table, including unreported usage and failed calls as `unmeasured`, never `$0`;
- a compact per-item table showing whether the effect is broad or driven by one task;
- a methodology appendix containing run spec, hashes, schedule seed/order, judge agreement, calibration evidence, diagnostics, and raw-artifact pointers.

This mirrors the OpenRouter-native shape—tool behavior, avoided behavior, completion/quality, a decision, failures, and cost—while keeping MemBench's stronger causal controls visible. The normal offline suite remains the PR gate; live model evals belong in a separately budgeted manual or scheduled workflow.

### Cost shape (from measured v0.1 rates)

- Task-aware reference generation: single call per item (~$0.10–0.50 cached) — replaces nothing (hand-authored notes were $0 but unscalable); no replay needed.
- Calibration: ~$1/item, saves ~$3–4/item of null matrix spend at current rates.
- The observe pass remains the dominant term (30–34M cumulative prompt tokens on large items); prompt caching (landed in v0.1) is the mitigation. Context length is a hard gate: observers under ~450k ctx cannot sit the large items at all — report this as a finding, not a bug.

## Implementation deltas

1. `controls.ts`: `taskAwareOracle(item, model)` via the existing observe transport (one call, `cache_control` on); emit per-fact event-id/quote provenance and mechanically verify it before stripping provenance from the seeded observations.
2. `cli.ts calibrate --spec …`: runs the independent gate, stamps eligibility and calibration evidence into the run manifest (not into frozen items), and never reuses calibration calls as scored rows.
3. `run-stage.ts`: build a seeded, round-robin randomized execution schedule; persist its seed, exact order, effective model/provider ids, prompt hashes, and harness versions.
4. `scoreboard.ts`: replace `% of oracle savings` with paired per-item floor delta + reference gap; add memory-attributed-hit and uncertainty fields; promote schema adherence to the reported table; render the Ori-shaped decision/failure/cost front page and permit `insufficient evidence`.
5. `measure.ts`: judge prompt gains the injection block for memory-attributed-hit scoring, requires cited evidence/consequence, and blinds model/variant identity; add the shuffled independent-judge audit path.
6. Corpus authoring guidance: task difficulty must be matched to executor capability — the calibration gate makes this measurable instead of judged.
7. `openrouter-agent.ts`: contain the `bash` tool in an OS-level sandbox so it matches the file tools' containment instead of relying on cwd + fork `HOME` alone (macOS `sandbox-exec` deny-write-outside-fork profile, or containerized forks). Motivation: Greptile P1 on PR #1 demonstrated host reads/writes outside the fork via `../` and absolute paths — accepted as a documented v0.1 trust-model limitation (local researcher-authored tasks only), must be closed before any corpus item or model not authored/chosen by the operator is allowed.
